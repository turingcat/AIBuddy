# HeyBuddy 产品目标与功能规划

@author: logic
@date: 2026-08-11

> 本文档定义 HeyBuddy 的**产品目标与功能边界**，作为后续设计与实现的基础。技术实现方案（登录如何落地、配置如何改写、白名单如何维护等）属于后续阶段，本文不展开。

---

## 1. 产品定位

HeyBuddy 当前是 goose 的私有 fork，原生形态是一个**面向开发者的开放工具**：用户自行配置 provider、自行填写 API key、自由扩展。

本次规划将其转变为一个**面向终端用户的受控桌面产品**：

> 一个桌面端 AI 助手。用户必须登录 HeyBuddy 自己的账号体系后才能发起对话；模型能力由官方服务端按用户身份下发，用户只需从可用模型列表中选择模型名称，全程不接触 provider、API key、base_url 等任何模型配置概念。

这是一次**从「工具」到「产品」的定位翻转**：开放配置 → 受控消费。

## 2. 现状背景（基于代码探查）

| 维度 | 现状 |
|---|---|
| 桌面 UI | Electron + React 应用。后端是本地 spawn 的 `goose serve` 二进制，UI 通过 ACP（WebSocket）与之通信。 |
| 模型配置 | 后端内置约 63 个 provider。**当前 UI 允许用户自由增删改「自定义 provider」、自由填写任意 API key / base_url**。本仓库已含 `zai.json`、`zhipu.json`（GLM 系）。 |
| 应用登录 | **完全不存在**。仓库内所有 `login/auth/token` 相关代码均属于「模型 provider 的 API key / OAuth」，与「HeyBuddy 用户账户」无关。唯一的进入门槛是 `OnboardingGuard`，判定条件是「是否配过 provider」。 |
| 其他入口 | goose 还带有 **CLI（`goose-cli`）** 和 **`goose serve` API**，二者均能绕过桌面 UI 配置任意 provider。 |

## 3. 三大目标的功能定义

### 目标①  模型受控（用户不可自配）

**功能定义：**
- provider、API key、base_url 等**所有模型配置概念对用户不可见**（桌面端隐藏全部相关配置入口）。
- 这些配置值**由登录态下发、在后台写入**，用户无感。
- 用户唯一可操作的模型行为：**从服务端下发的模型列表中，选择使用的模型名称**。
- 模型列表来自登录后服务端返回的 `base_url`，按用户身份返回该用户可用的模型集合。

**「硬编码」的含义：**
- 对用户而言是硬编码的——不可见、不可改。
- 实际取值是登录时动态下发的（base_url、key 均如此），并非编译期常量。

### 目标②  桌面版为重心

**功能定义：**
- 产品体验、功能改动**一律以桌面应用（`ui/desktop/`）为准**。
- **桌面版发行不向用户提供独立的 CLI**。goose 二进制仍随桌面应用打包、由桌面主进程以 `serve` 子命令内部启动，但用户终端中**不存在可用的 `goose` 命令**，从而堵住「用 CLI 绕过桌面 UI 配任意模型」这条侧门（否则目标①无法成立）。详见 6.1 的四层处理。

### 目标③  应用登录体系（新建，独立于模型登录）

**功能定义：**
- 全新建设的 **HeyBuddy 自有用户体系**，与任何模型 provider 的登录/OAuth 完全解耦。
- 登录是**发起对话的前置门槛**：未登录状态下应用可打开，但**不能发起对话**。
- 登录成功后，服务端下发：登录凭证、模型 `base_url`、模型 API key/鉴权凭证。
- 登录态需持久化（下次打开应用免重复登录），具体方式后续定。

## 4. 核心功能链路（闭合版）

```
打开桌面应用
   │
   ▼
[登录入口] ── 未登录 ──▶ 不能发起对话
   │
 登录成功，服务端下发: { 登录凭证, 模型 base_url, 模型 API key }
   │
   ▼
应用将 base_url 与 key 后台写入模型配置（用户不可见）
   │
   ▼
向该 base_url 请求，拿回该用户可用的「模型列表」
   │
   ▼
桌面端展示模型列表，用户从中选「模型名称」
   │
   ▼
发起对话（用选中模型名 + 注入的 base_url / key）
```

## 6. 设计张力与已定方案

本节原为待决策的张力清单，现已逐条讨论收口。每条给出结论、关键含义，以及仍保留为后续处理的部分。

### 6.1 CLI / `goose serve` 的去留 —— 已定：代码保留，二进制随桌面打包但不作为独立 CLI 发布

> 关键前提：`goose` 是**同一个二进制**（编译自 `crates/goose-cli`），兼具双重身份——`goose serve` 子命令是**桌面应用的后端**，其余子命令（`goose configure` / `goose run` 等）是用户可直接敲的 **CLI**。桌面应用运行时必须 spawn `goose serve`，故该二进制不可或缺。

- **结论：B**，并按以下四层准确执行：
  - **构建**：goose 二进制**必须构建**——桌面应用要用它的 `serve` 能力。
  - **打包**：goose 二进制**随桌面应用打包**，作为 app 的内部资源随 Electron 包分发。
  - **发布**：**不**作为独立 CLI 工具向用户发布——用户终端中**不会**出现一个可用的 `goose` 命令（不提供任何「装 CLI」的途径）。
  - **启动**：桌面主进程启动时以 `serve` 子命令 spawn 它，作为内部后端**仅监听 loopback**，用户不感知、无外部可访问入口。
- **如何堵住「用户用 CLI 配模型」这条侧门**：goose 二进制躺在 app 资源目录内、**不在系统 PATH 上**，故用户在终端敲 `goose` 找不到命令。仅手动翻进 app 目录取二进制者才能运行——即 6.1 中「B 挡不住自行探索者」的已知边界。
- **仓库代码策略**：保留 `crates/goose-cli` 全部代码不删（便于与上游 goose 同步），仅在打包/发布环节做上述区分。
- **关键含义**：目标用户不含「会自行编译 Rust 或翻进 app 目录的人」，对普通终端用户而言目标①的侧门已堵。
- **保留为后续加固项（暂不做）**：运行时禁用配置写入能力（原 C 选项）——即即便有人拿到二进制运行，也使其无法改 provider 配置。当前阶段不实现，记为后续安全加固候选。

### 6.2 登录态与现有 `OnboardingGuard` 的关系 —— 已定：替换

- **结论：A**。保留 `OnboardingGuard` 这个「进入主界面前的一道闸」的**壳子**，但**内核整体替换**：
  - 判定条件从「是否配过 provider」改为「是否登录」。
  - 登录通过后，由服务端下发的配置**后台静默注入**，直接进入主界面。
  - 老的 provider onboarding 流程（`ProviderSelector` / `ProviderConfigForm` / `LocalModelPicker` 等）在桌面版中**作废**。
- **产品姿态**：纯登录页 —— 未登录时应用只呈现登录入口，不进入主界面、不能发起对话。

### 6.3 「配置后台写入」与 goose 既有配置体系 —— 已定：独立登录态文件 + 环境变量注入

- **结论：B**。
  - 登录下发的 `base_url` 与 `key` 写入 **HeyBuddy 自己的独立凭证文件**（存于应用 userData 私有目录），**不碰 goose 的 config.yaml / keyring**。
  - 桌面应用 spawn `goose serve` 子进程时，将这份凭证**以环境变量注入**；利用 goose「环境变量 > config.yaml > keyring」的优先级，注入值天然压过任何文件残留配置，**无需主动清理用户既有配置**。
  - **登出 = 删除该独立凭证文件**，零误伤，不存在多账号残留凭证的安全风险。
- **隐含决定**：凭证落盘持久化 ⇒ **记住登录态，免重复登录**（下次打开应用无需重新输密码）。
- **保留为后续可选升级**：若日后对凭证安全性要求更高，可再升级到系统 keyring 或纯内存态。

### 6.4 目标①与目标③的功能耦合 —— 已定：三阶段实施

- **结论**：按三阶段顺序实施，阶段二用桩接口，不阻塞服务端设计。
  - **阶段一（目标① 减法，独立可做）**：隐藏桌面端所有 provider / API key / base_url 配置入口，禁用自定义 provider 的增删改。不依赖登录，可立即验证。
  - **阶段二（目标③ 登录闸 + 6.3 注入骨架，桩接口）**：加登录入口与未登录拦截（6.2 的 A）、登录态持久化（6.3 的 B）、凭证独立文件 + 环境变量注入 `goose serve`。此阶段使用 **mock 桩接口**，无需真实服务端就绪。
  - **阶段三（目标① 加法 + 真实对接）**：服务端就绪后，将阶段二的桩替换为真实登录接口 / 模型列表接口；登录后从真实 base_url 拉取模型列表，用户选模型名发起对话，端到端跑通。
- **并行机会**：服务端 API 可与阶段一、阶段二**并行设计与开发**，其契约见第 7 节。

## 7. 服务端接口契约（供服务端开发与阶段三对接）

> 服务端尚未实现，需边做边设计。本节列出桌面端对服务端的**最小契约要求**，作为服务端开发的依据与阶段三对接的依据。其中 7.2 / 7.3 已确定为标准 OpenAI 兼容协议；7.1 登录接口的字段细节仍待服务端定。

桌面端需要服务端提供两类能力：

### 7.1 登录接口
- **用途**：验证 HeyBuddy 用户身份，返回登录凭证与模型下发信息。
- **入参建议**：账号标识（用户名 / 邮箱 / 手机号，待定）、凭据（密码 / 验证码，待定）。
- **返回建议**：
  - 登录凭证（token，后续用于鉴权与免重复登录）。
  - 用户信息（用户标识、展示名等，用于 UI 展示与可能的差异化）。
  - 模型 `base_url`（该用户专用的模型服务入口）。
  - 模型 API key / 鉴权凭证（用于访问上述 base_url）。
- **注**：`base_url` 与 `key` 是否在登录响应中一次性下发，还是在登录后由单独接口换取，二选一，待服务端定。本文按「登录即下发」描述（见第 4 节链路）。

### 7.2 模型列表接口（挂在 base_url 上，标准 OpenAI 协议）
- **用途**：返回该用户可用的模型白名单，供桌面端展示与选择。
- **协议**：**标准 OpenAI `/v1/models` 接口**——`GET {base_url}/v1/models`，请求头 `Authorization: Bearer {key}`，响应体为标准 `{ "data": [ { "id": "...", ... } ] }` 结构。服务端无需另造协议。
- **鉴权**：使用登录下发的 key / 凭证。
- **字段映射**：响应中每个模型的 `id` 即用户在桌面端选择的「模型名称」。
- **goose 侧对接**：直接复用 goose 既有 `openai` engine 与 `dynamic_models` 机制（仓库中 `zhipu.json` 即同类 OpenAI 兼容 provider），无需新增引擎。

### 7.3 对话接口（挂在 base_url 上，OpenAI 兼容）
- **用途**：承载实际对话。
- **协议**：**OpenAI 兼容**——`POST {base_url}/v1/chat/completions`，与 7.2 同源。goose `openai` engine 现成支持，含流式（SSE）。
- **鉴权**：使用登录下发的 key / 凭证。
- **注**：base_url 指向的服务端为 OpenAI 兼容网关（与智谱/Z.AI GLM 系的 OpenAI 兼容入口同形态），故模型列表与对话共用同一 engine 声明。

> 第 4 节核心链路对上述三类接口的调用顺序即：登录接口 → 写入 base_url/key → 模型列表接口 → 用户选模型 → 对话接口。
